# Generated API Types

## Overview

Make the backend OpenAPI file the source of truth for the frontend API types. The backend models the three totals lists with three precise row structs, and documents the `status` and `group_by` enums. The frontend generates `src/modules/shared/api-schema.d.ts` from `../backend/docs/openapi/openapi.json`, and its API types are aliases of that file. The generated file is committed, and `pnpm api:check` fails when it is stale.

No JSON response changes. The backend struct split changes only the documented schema, and the golden and contract tests prove the bytes are the same.

## Requirements

### Backend

- `GET /movements/totals` uses three response structs:
  - `AssetTotalRow`: `direction`, `usd_value` and `unpriced_count` are always present.
  - `FeeTotalRow`: no `direction`; `usd_value` and `unpriced_count` are always present.
  - `CounterTotalRow`: `direction` is always present; it has no USD fields.
- `TotalsResponse.Status` documents `pending`, `completed`, `failed`.
- `TotalsResponse.GroupBy` documents `category` and `null`.
- The JSON responses keep the same keys, values and order.
- Regenerate `docs/openapi/openapi.json`.
- Tests assert the enums and the three row schema references, so a future annotation edit can't widen the generated types silently.

### Frontend

- `src/modules/shared/api-schema.d.ts` is generated by `openapi-typescript` 7.13.0 and committed.
- `src/modules/shared/api-types.ts` exports `Schemas` and `Operations` aliases.
- `movements/types.ts`, `snapshots/types.ts`, `categories/types.ts` and `shared/session.ts` derive their API types from the generated schemas.
- Query parameter types come from `operations["..."]["parameters"]["query"]`.
- Response envelopes come from the generated schemas where the API functions use one.
- The generated file is ignored by ESLint.
- `pnpm api:generate` regenerates the file; `pnpm api:check` fails when it is stale; `pnpm verify` runs the check, lint, tests and build.
- `OPENAPI_PATH` overrides the default `../backend/docs/openapi/openapi.json` with another file or an http(s) URL.

### Deployment

- Backend pipeline: `make test`, which includes `openapi-check`, the database tests and the contract tests.
- Frontend pipeline: `pnpm verify`.
- Deploy the matching backend and frontend pair, or keep API changes additive. Generated types are compile-time only and don't protect an old frontend from a breaking backend deploy.

## Acceptance Criteria

- **Given** the backend OpenAPI file, **when** `pnpm api:generate` runs, **then** the committed generated file is rewritten byte-for-byte the same.
- **Given** a changed backend schema and an unchanged generated file, **when** `pnpm api:check` runs, **then** it exits non-zero.
- **Given** `GET /movements/totals`, **then** the generated types have `assets: AssetTotalRow[]`, `fees: FeeTotalRow[]` and `counter: CounterTotalRow[]`, with the fields each row always carries.
- **Given** `GET /movements/totals`, **then** generated `status` is `("pending" | "completed" | "failed")[]` and `group_by` is `"category" | null`.
- **Given** the old hand-written API types, **then** the generated aliases are structurally identical.
- **Given** the backend suite, **then** the totals JSON bodies are unchanged.

## Out of Scope

- Runtime response validation in the frontend.
- Changing the wire JSON of `GET /movements/totals`.
- Generating the frontend file during `pnpm build`; the file is committed so builds don't need the backend checkout or network.
